## 1. Java·Spring Boot 버전

- 날짜: 2026-11-22
- 고른 사람: 직접 선택

**문제**: 최신 버전을 쓸지, 학습 자료가 많은 버전을 쓸지.

**고려한 선택지**

| 선택지 | 장점 | 단점 |
|---|---|---|
| Spring Boot 4.2.0 + Java 25 | 무료 지원이 2027-12-31까지로 가장 길다. Java 25는 최신 LTS | 국내 자료 상당수가 3.x 기준이다. 4.2.0은 2026-11-19에 나온 버전이다 |
| Spring Boot 3.5.16 + Java 21 | 국내 강의·블로그 대부분이 이 기준이다 | 무료 지원이 2026-06-30에 끝났다(3.5.16이 마지막 무료 패치). Spring Initializr에서 더 이상 만들 수 없다 |

**선택과 이유**: Spring Boot 4.2.0 + Java 25. 실제로 배포할 서비스라 보안 패치가 계속 나오는 버전이 필요하다. 공부할 핵심 개념(HTTP API, JPA, 트랜잭션, 테스트)은 3.x와 같다.

**결과: 3.x 자료를 볼 때 다른 점** (새로 발견할 때마다 추가한다)

| 3.x 자료 | 이 프로젝트 (4.2) |
|---|---|
| `spring-boot-starter-web` | `spring-boot-starter-webmvc` |
| 테스트 의존성은 `spring-boot-starter-test` 하나 | 기능별 테스트 스타터 (`spring-boot-starter-webmvc-test`, `spring-boot-starter-data-jpa-test` 등) |
| `org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc` | `org.springframework.boot.webmvc.test.autoconfigure.AutoConfigureMockMvc` |
| Flyway는 `flyway-core` + `flyway-mysql` | `spring-boot-starter-flyway` + `flyway-mysql` |
| `@MockBean` | 없어졌다. Spring Framework의 `@MockitoBean`을 쓴다 |
| JUnit 5 | JUnit 6.1 (`@Test` 같은 쓰는 법은 같다) |
| Testcontainers 1 (`org.testcontainers:mysql`, `org.testcontainers.containers.MySQLContainer`) | Testcontainers 2 (`testcontainers-mysql`, `org.testcontainers.mysql.MySQLContainer`) |

## 2. 비밀 정보(DB 비밀번호) 관리

- 날짜: 2026-11-22
- 고른 사람: 직접 선택

**문제**: DB 비밀번호를 깃에 올리지 않으면서, 로컬에서 docker compose와 Spring Boot가 같은 값을 써야 한다.

**고려한 선택지**

1. 루트의 `.env` 파일 하나를 docker compose와 Spring Boot가 같이 읽는다.
2. `application-local.yml`(깃 제외)에 둔다. 국내 자료에서 가장 흔하지만, 같은 비밀번호를 compose용 파일에도 적어서 두 곳을 맞춰야 한다.
3. IDE 실행 설정에 환경 변수를 넣는다. 파일은 없지만, 설정이 IDE 안에 숨어 있어서 다시 세팅하기 번거롭다.

**선택과 이유**: 1번. 비밀번호를 한 곳에만 적으면 된다. 배포 서버에서도 같은 이름의 환경 변수를 넣으면 되므로 로컬과 배포의 구조가 같다.
- docker compose는 같은 폴더의 `.env`를 자동으로 읽는다.
- Spring Boot는 `spring.config.import: optional:file:../.env[.properties]`로 읽는다. 파일이 없으면(CI, 배포 서버) 건너뛴다.

**결과**: `git check-ignore`로 `.env`가 깃에서 빠지는 것을 확인했다. 깃에는 값이 빈 `.env.example`만 있다. 로컬 비밀번호는 무작위 24자로 만들었다.

## 3. 로컬 DB와 테스트 DB

- 날짜: 2026-11-22
- 고른 사람: 직접 선택

**문제**: 개발과 테스트에 쓸 MySQL을 어떻게 띄울지. "한 메뉴에 2표" 같은 규칙 위반을 DB 제약 조건과 동시 요청까지 실제와 같게 검증해야 한다.

**고려한 선택지**

1. Docker: 로컬은 Docker Compose로 MySQL을 띄우고, 테스트는 Testcontainers가 테스트마다 실제 MySQL 컨테이너를 띄운다.
2. MySQL을 Windows에 직접 설치하고, 테스트는 H2(메모리 DB)로 한다.

**선택과 이유**: 1번. H2는 MySQL과 잠금, 제약 조건, SQL 문법이 조금씩 달라서 정합성 테스트 결과가 실제와 어긋날 수 있다. MySQL 버전을 파일에 적어두면 내 PC, CI, 배포 서버가 모두 같은 MySQL을 쓴다. 배포도 Docker Compose라 미리 익숙해진다.

**대가**: 테스트를 돌릴 때 Docker가 켜져 있어야 하고, 컨테이너를 띄우는 시간만큼 테스트가 느리다.

**결과**: CI(GitHub Actions)에서 Testcontainers가 MySQL 9.7 컨테이너를 띄워 테스트가 통과했다.
- 테스트 1개 기준으로 test 단계가 약 30초 걸렸다(MySQL 컨테이너 시작, 스프링 실행 포함, 2회 측정 29~30초).
- CI의 백엔드 작업 전체는 약 1분 25초였다.
- 테스트 설정이 같은 테스트끼리는 스프링이 실행 환경(컨텍스트)과 컨테이너를 다시 쓰므로, 테스트 개수만큼 그대로 느려지지는 않는다. 테스트가 늘어난 뒤 다시 잰다.

## 4. 테이블 관리 방법

- 날짜: 2026-11-22
- 고른 사람: Claude가 제안, 승인함

**문제**: 테이블을 어떻게 만들고 바꿀지.

**고려한 선택지**

1. Flyway: 테이블 변경 이력을 SQL 파일(`V1__...sql`)로 남기고, 서버가 켜질 때 아직 적용 안 된 파일만 순서대로 실행한다.
2. JPA 자동 생성(`ddl-auto: create` 또는 `update`)
3. SQL을 손으로 실행

**선택과 이유**: 1번. JPA는 테이블을 만들지 않고 엔티티와 맞는지 검사만 한다(`ddl-auto: validate`).
- 자동 생성은 운영 DB를 의도치 않게 바꿀 수 있다.
- 손으로 실행하면 환경마다 테이블 구조가 달라지기 쉽다.
- SQL 파일이 PR에 그대로 보여서 리뷰하기 쉽다.

**대가**: 테이블을 바꿀 때마다 SQL 파일을 새로 써야 한다.

## 5. MySQL 버전

- 날짜: 2026-11-22
- 고른 사람: Claude가 고름

**고려한 선택지**: 9.7 LTS, 8.4 LTS, 26.x Innovation

## 6. 웹 방식: Spring MVC와 WebFlux

- 날짜: 2026-11-22
- 고른 사람: Claude가 고름

**문제**: SSE로 방 참여자 모두에게 실시간으로 알려야 한다.

**고려한 선택지**

1. Spring MVC + `SseEmitter`
2. Spring WebFlux (반응형, `Flux`로 SSE)

**선택과 이유**: 1번. JPA는 블로킹 방식이라 MVC와 자연스럽게 맞고, 자료도 많다. `SseEmitter`는 연결마다 요청 스레드를 붙잡지 않으므로, 서버 한 대에 방 단위의 작은 규모라면 충분하다.

**같이 정한 것**: `spring.jpa.open-in-view: false`. 켜두면 SSE처럼 오래 열린 요청이 끝날 때까지 DB 커넥션을 붙잡을 수 있다.

**나중에 다시 볼 것**: 서버를 여러 대로 늘리면 서버끼리 이벤트를 전달할 방법(예: Redis Pub/Sub)이 필요하다.

## 12. 참여자 식별 방식 (보안)

- 날짜: 2026-11-22
- 고른 사람: 직접 선택

**문제**: 회원가입 없이도 새로고침한 사람을 같은 참여자로 알아보고(투표 수 제한 등), 다른 사람이 그 참여자인 척하지 못하게 해야 한다.

**고려한 선택지**

1. 서버가 만든 무작위 토큰을 HttpOnly 쿠키로 준다.
2. 토큰을 localStorage에 저장하고, 요청마다 헤더로 보낸다.
3. 토큰을 주소(URL)에 넣는다.

**선택과 이유**: 1번.
- HttpOnly 쿠키는 자바스크립트가 읽을 수 없다. 메뉴 이름처럼 남이 입력한 글을 화면에 보여주는 서비스라, 악성 스크립트가 끼어드는 공격(XSS)에도 토큰을 빼 갈 수 없다. localStorage는 스크립트가 읽을 수 있다.
- SSE 연결(EventSource)은 헤더를 붙일 수 없지만, 쿠키는 자동으로 보낸다. 2번은 SSE 때 토큰을 주소에 넣어야 해서 서버 로그 등에 남는다(3번과 같은 문제).
- 쿠키 경로(Path)를 `/api/rooms/{방 코드}`로 정해서 방마다 다른 참여자로 따로 관리된다.
- SameSite=Lax로 다른 사이트에서 몰래 보내는 요청에는 쿠키가 붙지 않게 하고, 배포(HTTPS)에서는 Secure를 켠다.
- 서버에는 토큰 원본이 아니라 SHA-256 해시만 저장한다. DB가 유출돼도 참여자 행세를 할 수 없다. 토큰은 사람이 정한 비밀번호가 아니라 추측할 수 없는 32바이트 무작위 값이라, 비밀번호용 느린 해시(bcrypt 등)는 필요 없다.

**결과**: HttpOnly·Path·SameSite 설정, DB에 해시만 저장되는지, 다른 방 쿠키를 거절하는지를 테스트로 확인했다.

**한계**: 시크릿 창이나 다른 브라우저로 들어오면 다른 참여자가 된다. 회원가입이 없는 익명 서비스의 구조적 한계다.

## 13. 방 링크 코드

- 날짜: 2026-11-22
- 고른 사람: 직접 선택

**고려한 선택지**

| 선택지 | 문제 |
|---|---|
| 1, 2, 3 같은 자동 증가 번호 | 번호를 바꿔 가며 남의 방에 들어갈 수 있다 |
| UUID (36자) | 안전하지만 링크가 길다 |
| 무작위 6자 | 경우의 수가 62^6 ≈ 5.7 × 10^10으로 적다 |
| 무작위 10자 (영문 대소문자와 숫자) | 경우의 수 62^10 ≈ 8.4 × 10^17 |

**선택과 이유**: 무작위 10자. 보안용 난수(SecureRandom)로 만들어 다음 값을 예측할 수 없다.

**같이 정한 것**: DB의 코드 칼럼을 대소문자 구분 정렬(`ascii_bin`)로 만들었다. MySQL 기본 정렬(`utf8mb4_0900_ai_ci`)은 대소문자를 구분하지 않아서 `aB`와 `Ab`가 같은 방으로 취급된다.

**결과**: 코드의 대소문자를 바꾸면 없는 방(404)이 되는지 테스트로 확인했다.

## 14. 정원 50명과 동시 참여

- 날짜: 2026-11-22
- 고른 사람: 정원(50명)은 직접 선택, 동시성 처리 방법은 Claude가 고름

**문제**: 여러 명이 동시에 참여하면 "인원 세기 → 정원 확인 → 추가"가 서로 섞인다. 두 사람이 동시에 "49명이니 들어가도 된다"고 판단하면 51명이 된다(확인과 실행 사이의 경쟁 상태).

**고려한 선택지**

1. 비관적 락: 방을 잠그고(`SELECT ... FOR UPDATE`) 인원을 센 뒤 추가한다. 같은 방 참여는 한 명씩 차례로 처리된다.
2. 조건부 UPDATE: 방에 인원 칼럼을 두고 `UPDATE ... SET 인원 = 인원 + 1 WHERE 인원 < 50`으로 한 번에 늘린다. 잠그는 시간이 가장 짧지만 인원 칼럼을 따로 맞춰 관리해야 한다.
3. 낙관적 락(`@Version`): 잠그지 않고, 동시에 바뀌면 한쪽을 실패시킨다. 실패하면 다시 시도하는 코드가 필요하고, 사람이 몰리면 재시도가 많아진다.

**선택과 이유**: 1번. 코드가 가장 단순하고 결과가 정확하다. 한 방에 최대 50명이라 차례를 기다리는 시간이 문제 되지 않는다. 앞으로 단계 전환(시간 초과, 방장 버튼, 모두 끝냄이 동시에 일어날 수 있다)도 같은 방식으로 한 방의 일을 순서대로 처리할 수 있다.

**결과**: 60명이 동시에 참여하는 테스트를 만들었다.
- 잠금이 있으면 매번 방장 포함 정확히 50명이 참여하고 10명은 정원 초과로 거절된다.
- 잠금을 빼고 3번 돌리면 55명, 57명, 59명이 참여했다. 정원 50명을 넘는다.

## 15. SSE 설계

- 날짜: 2026-11-22
- 고른 사람: Claude가 고름

- **보내는 내용**: 바뀐 부분만이 아니라 방 상태 전체를 보낸다. 바뀐 부분만 보내면 데이터는 작지만, 하나라도 놓치면 화면이 어긋난다. 전체를 보내면 다시 연결했을 때 현재 상태만 받으면 된다.
- **개인 정보 없음**: 모두에게 같은 내용을 보내므로, 누가 방장인지는 SSE에 넣지 않는다. 방장 여부는 참여·조회 응답으로 본인에게만 준다. (기능 3에서 바뀜: 연결마다 그 사람 본인의 정보를 붙여 보낸다. 27번)
- **커밋 후 전송**: 참여가 DB에 커밋된 뒤에만 보낸다(`@TransactionalEventListener(AFTER_COMMIT)`). 커밋 전에 보내면 롤백된 상태를 보여줄 수 있다.
- **순서 보장**: 같은 방에 대해 "DB에서 최신 상태 읽기 + 보내기"를 한 번에 하나씩 한다. 그러지 않으면 먼저 읽은 오래된 인원 수가 나중에 도착해 화면에 남을 수 있다.
- **연결 유지**: 25초마다 하트비트(내용 없는 주석 줄)를 보내고, 30분이 지나면 서버가 연결을 닫는다. 브라우저(EventSource)가 자동으로 다시 연결하고 현재 상태를 받는다.
- **자격 확인**: EventSource가 쿠키를 자동으로 보내므로 참여자만 연결할 수 있다.

**결과**: 실제 서버에 HTTP로 연결하는 테스트로, 연결하자마자 현재 상태를 받고 누가 들어오면 바뀐 인원 수를 받는 것을 확인했다. Vite 개발 서버의 프록시를 거쳐도 동작했다.

**나중에 다시 볼 것**: 연결 목록을 서버 메모리에 들고 있어서, 서버를 여러 대로 늘리면 서버끼리 이벤트를 전달할 방법(예: Redis Pub/Sub)이 필요하다.

## 17. 그 밖의 구현 결정

- 날짜: 2026-11-22
- 고른 사람: Claude가 고름

- **Lombok을 쓰지 않는다.** 국내 자료 대부분이 `@Getter` 같은 Lombok 어노테이션을 쓴다. 이 프로젝트는 처음 공부할 때 숨은 코드 없이 다 보이도록 getter를 직접 쓰고, 요청·응답 객체는 Java record로 만든다. 나중에 필요하면 도입할 수 있다.
- **시각**: `Instant`로 다루고 UTC로 저장한다. 현재 시각은 주입한 `Clock`으로만 얻어서, 단계 타이머 테스트에서 시간을 마음대로 바꿀 수 있게 한다.
- **프론트 페이지 이동**: React Router 8을 쓴다.
- **개발 모드의 참여 중복**: React 개발 모드(StrictMode)는 화면을 두 번 그려서 참여 요청이 동시에 두 번 나간다. 쿠키를 받기 전이라 참여자가 둘이 되므로, 같은 방 참여 요청은 하나로 합친다.

## 18. 제안 단계 실시간 공개와 합치기 규칙 (서비스 규칙 변경)

- 날짜: 2026-11-22
- 고른 사람: 문제 제기와 방향은 직접, 세부안은 Claude가 제안하고 승인함

**문제**: 다른 사람 메뉴를 보면 생각이 바뀐다. 원래 규칙에서는 합치기 단계에서야 다른 사람 메뉴가 보여서, 그때 떠오른 생각을 반영할 방법이 없었다.

**고려한 선택지**

1. 합치기 단계에서 자기 메뉴를 마지막으로 한 번 바꾸게 한다(처음 아이디어).
   - AI가 묶은 뒤에 메뉴가 바뀌어서, 바뀐 메뉴가 다른 메뉴와 비슷해지면 합치기가 막으려던 표 갈림이 다시 생긴다.
   - 합치기에 동의한 뒤에 바꾸는 경우처럼 새로 정할 규칙이 많아진다.
2. 제안 단계 동안 제안된 메뉴를 실시간으로 보여주고, 단계가 끝나기 전까지 자기 메뉴를 바꾸거나 취소하게 한다.
3. 제안과 합치기 사이에 짧은 수정 단계를 따로 둔다. 깔끔하지만 단계가 하나 늘어 전체 시간이 길어진다.

**선택과 이유**: 2번. AI가 최종 메뉴로 묶으므로 표 갈림이 다시 생기지 않고, 합치기 단계의 규칙은 그대로 둘 수 있다.
- 대가: 모두가 제안하면 바로 다음 단계로 넘어가서, 맨 마지막에 나온 메뉴를 보고 바꿀 시간은 없다.
- 대가: 인원이 아주 적으면 방금 올라온 메뉴로 누가 냈는지 짐작될 수 있다. 목록 순서를 섞어 보여주면 줄일 수 있다.

**직접 합치기는 어디에 둘지**

| 안 | 문제 |
|---|---|
| 제안 단계로 옮기기 | 메뉴가 계속 바뀌는 단계라, 동의를 기다리는 사이에 상대가 메뉴를 바꾸면 꼬인다 |
| 아예 없애기 | 가장 단순하지만, AI가 놓친 메뉴를 사람이 합칠 방법이 없다 (동네 가게 이름만 쓴 경우, 같은 메뉴인지 사람마다 생각이 다른 경우, AI가 응답하지 않을 때) |
| **합치기 단계에 그대로 두기 (선택)** | 메뉴가 고정된 뒤라 꼬임이 없고, AI가 놓친 것을 사람이 보완한다 |

처음에는 단순함을 우선해 "아예 없애기"를 추천했지만, AI가 놓치는 경우가 생기지 않느냐는 질문을 받고 다시 따져 보니 사람의 보완 수단이 필요했다.

**AI가 덜 놓치게 하는 장치**
- 입력창에서 가게 이름만 쓰지 말고 음식 이름을 함께 쓰도록 안내한다(예: "할매집 제육").
- AI는 같은 메뉴인지 애매하면 묶는다. 잘못 묶이면 거절 한 번이면 되지만, 놓치면 표가 갈려 손해가 더 크다.

**결과**: 제안 단계는 기능 2, 합치기는 기능 3에서 구현한다. 기능 3에서는 실제 메뉴 이름 30~50개로 시험 문제를 만들어 후보 AI들의 정확도를 잰 뒤 고르고, 직접 합치기의 세부 규칙(한 메뉴에 요청이 여러 개 올 때, AI 그룹에 이미 들어간 메뉴에 요청할 때 등)을 함께 정한다.

## 19. 단계 진행 방식 (타이머와 동시성)

- 날짜: 2026-11-23
- 고른 사람: Claude가 고름

**문제**: 단계는 시간 초과, 모두 끝냄, 방장 버튼의 세 가지 길로 넘어간다. 셋이 동시에 일어나도 한 번만 넘어가야 하고, 서버가 재시작돼도 시간이 지켜져야 한다.

**고려한 선택지 (타이머)**

1. DB에 끝나는 시각을 저장하고, 1초마다 시간이 다 된 방을 찾아 넘긴다.
2. 서버 메모리에 방마다 "N초 뒤 실행"을 예약한다. 정확하지만, 서버가 재시작되면 예약이 사라지고 서버를 늘리면 어느 서버가 맡을지 정해야 한다.
3. 타이머 없이, 누군가 요청할 때 시간이 지났는지 확인한다. 아무도 요청하지 않으면 영원히 넘어가지 않는다.

**선택과 이유**: 1번. 끝나는 시각이 DB에 있어서 재시작해도 지켜진다(재시작 동안 시간이 지난 방은 켜지자마자 넘어간다). 최대 1초 늦을 수 있지만 점심 메뉴를 고르는 데는 충분하다.

**동시성**: 세 길 모두 방을 잠근 뒤(`SELECT ... FOR UPDATE`) 조건을 다시 확인하고 넘긴다. 잠그기 전에 다른 길이 이미 넘겼다면 다시 확인할 때 걸러진다. 서버를 여러 대로 늘려도 같은 방은 잠금 때문에 한 번에 한 서버만 처리하므로 두 번 넘어가지 않는다.

**결과**
- 실제 서버에서 제안 30초짜리 방을 시작하고 아무것도 하지 않고 기다렸더니, 끝나는 시각 0.15초 뒤에 다음 단계 상태가 SSE로 왔다(1회 측정).
- 50명이 동시에 제안하는 테스트에서 메뉴 50개가 모두 저장되고 단계는 한 번만 넘어갔다.

## 20. 방장 버튼 두 번 누르기 막기

- 날짜: 2026-11-23
- 고른 사람: Claude가 고름

**문제**: 방장이 "시작"을 두 번 누르면(더블 클릭, 느린 네트워크에서 다시 누르기) 두 단계가 넘어갈 수 있다.

**고려한 선택지**

1. 요청에 방장 화면에 보이던 단계(`from`)를 같이 보내고, 서버의 단계가 이미 다르면 409로 거절한다.
2. 프론트에서 버튼을 잠깐 비활성화한다. 탭이 두 개거나 네트워크가 느리면 막지 못한다.
3. 요청마다 고유 번호(멱등 키)를 붙이고 서버가 처리한 번호를 기억한다. 확실하지만 번호를 저장하고 관리해야 한다.

**선택과 이유**: 1번. 서버에서 확실히 막고, 따로 저장할 것도 없다.

**결과**: `from` 확인을 잠깐 빼고 테스트해 보니, 동시에 두 번 누른 "시작"이 둘 다 성공했다. 메뉴가 없는 방이라 두 번째 요청이 제안 단계를 통째로 건너뛰고 랜덤 선택까지 넘겼다. 확인을 넣으면 한 번만 성공하고 나머지는 409로 거절된다.

## 22. 남은 시간 표시 (시계 차이 보정)

- 날짜: 2026-11-23
- 고른 사람: Claude가 고름

**문제**: 휴대폰 시계는 서버 시계와 몇 초씩 다를 수 있다. 끝나는 시각만 보내면 휴대폰마다 남은 시간이 다르게 보인다.

**고려한 선택지**

1. 끝나는 시각과 서버의 현재 시각을 같이 보내고, 받는 순간 두 시계의 차이를 계산해 보정한다.
2. 남은 초만 보낸다. 받은 뒤 화면이 직접 줄여야 하고, 메시지가 오가는 시간만큼씩 어긋난다.
3. 서버가 매초 남은 시간을 보낸다. 정확하지만 SSE 메시지가 1초마다 생긴다.

**선택과 이유**: 1번. 메시지는 상태가 바뀔 때만 보내면서도 휴대폰 시계와 상관없이 맞게 보인다.

**같이 정한 것**
- 서버 시계를 1밀리초 단위로 끊었다. DB는 마이크로초까지 저장하지만 브라우저는 밀리초까지만 정확히 읽어서 둘을 맞췄다.
- HTTP 응답과 SSE 이벤트는 도착 순서가 바뀔 수 있어서, 화면은 서버 시각이 더 최신인 상태만 반영한다.

## 24. 합치기를 AI 없이 먼저 만들기 (서비스 규칙 변경)

## 25. 합치기 저장 구조

- 날짜: 2026-11-26
- 고른 사람: Claude가 고름

**문제**: "이 메뉴들을 합칠까요?"라는 질문과 사람마다의 답, 결과(대표 메뉴)를 어떻게 저장할까. 다음 PR의 직접 합치기(메뉴 2개짜리 질문)도 같은 방식으로 다뤄야 한다.

**고려한 선택지**

1. `merge_group`(질문 하나) + `merge_group_member`(그룹에 든 메뉴와 그 메뉴를 낸 사람의 답) 두 테이블
2. `menu` 테이블에 그룹 번호와 답 칼럼을 둔다. 테이블은 적지만, 한 메뉴가 여러 질문을 거치면(자동 그룹에서 거절한 뒤 직접 합치기 요청 등) 앞의 기록이 덮어써진다.
3. 그룹 하나를 JSON 칼럼에 통째로 저장한다. 읽고 쓰기는 쉽지만, 같은 메뉴가 두 번 들어가는 것 같은 실수를 DB가 막아 줄 수 없고 조건으로 찾기 어렵다.

**선택과 이유**: 1번. 질문 하나가 행 하나라서, 직접 합치기도 "메뉴 2개짜리 그룹"으로 똑같이 다룰 수 있다. `(merge_group_id, menu_id)`에 UNIQUE를 걸어 같은 메뉴가 한 그룹에 두 번 들어가는 것을 DB가 막는다.

**같이 정한 것**
- 합쳐진 메뉴는 지우지 않고 대표 메뉴를 가리키게 한다(`menu.merged_into_id`). 어느 메뉴가 어디로 합쳐졌는지가 남고, 낸 사람에게 "내 메뉴가 ○○로 합쳐졌어요"를 보여줄 수 있다.
- 답하지 않아서 "합치지 않기"로 처리된 경우는 답한 시각을 비워 둔다. 직접 거절한 것과 구분할 수 있다.

## 26. 화면에 내보내는 메뉴·그룹 번호

- 날짜: 2026-11-26
- 고른 사람: Claude가 고름

**문제**: 합치기 질문에 답하거나 직접 합치기를 요청하려면 메뉴와 그룹을 가리킬 번호가 필요하다. DB 번호(1, 2, 3...)를 그대로 보여주면 올라온 순서가 드러난다. 가장 작은 번호가 가장 먼저 낸 메뉴라는 것을 알 수 있다.

**고려한 선택지**

1. 무작위 UUID를 따로 저장해서 보여준다.
2. 방 코드처럼 10자 무작위 문자열을 만든다. 짧지만 겹칠 때 다시 만드는 처리가 필요하다.
3. DB 번호를 비밀 키로 바꿔서(HMAC 등) 보여준다. 따로 저장할 것은 없지만 처음 읽기 어렵다.

**선택과 이유**: 1번. 무작위 부분이 122비트라 겹칠 걱정 없이 Java 기본 기능(`UUID.randomUUID()`)으로 만든다. "안에서 쓰는 번호와 밖에 보여주는 번호를 나눈다"는 흔한 방법이다. 방 코드는 링크에 들어가서 짧아야 하므로 따로 둔다.

**같이 정한 것**
- 같은 이름의 메뉴끼리는 공개 번호 순으로 놓아서, 같은 이름끼리의 순서도 올라온 순서와 상관없게 했다.
- 메뉴 이름을 바꿀 때 번호도 새로 만들지 생각했지만 그만뒀다. 번호를 바꿔도 "메뉴 하나가 사라지면서 동시에 다른 메뉴가 생기는 것"이 보여서 같은 사람이 바꿨다는 것을 숨길 수 없다.

## 27. SSE로 사람마다 다른 정보 보내기

- 날짜: 2026-11-26
- 고른 사람: Claude가 고름

**문제**: 지금까지 SSE는 모두에게 같은 방 상태만 보냈고, 내 정보(me)는 내가 보낸 요청의 응답으로만 받았다. 합치기부터는 다른 사람의 행동으로 내 정보가 바뀐다. 예를 들어 그룹의 마지막 사람이 답하면 내 메뉴가 대표 메뉴에 합쳐진다. 기능 5의 "랜덤으로 뽑힌 사람에게만 알리기"도 같은 문제다.

**고려한 선택지**

1. SSE 연결마다 쿠키로 확인한 참여자를 기억해 두고, 보낼 때 그 사람의 정보를 붙인다.
2. SSE로 "방이 바뀌었다"는 신호만 받으면 화면이 내 정보를 다시 요청한다. 단순하지만 바뀔 때마다 참여자 수만큼 요청이 몰린다(50명이면 50번).
3. 화면이 방 상태를 보고 내 정보를 계산한다. 그러려면 방 상태에 "어느 메뉴가 누구 것인지"를 넣어야 해서 익명이 깨진다.
4. 정보가 바뀐 사람에게만 따로 이벤트를 보낸다. 보내는 양은 적지만, 매번 "누구의 정보가 바뀌었는지"를 정확히 골라야 해서 실수하기 쉽다.

**선택과 이유**: 1번. 화면은 HTTP 응답과 SSE를 똑같은 모양(방 상태 + 내 정보)으로 받아서 그대로 반영하면 된다. 누구의 정보가 바뀌었는지 고르지 않고 매번 모두의 정보를 새로 만든다. 다시 연결될 때도 서버가 지금 정보를 먼저 보내므로, 화면이 따로 다시 불러오던 코드도 지웠다.

**결과**
- 50명, 그룹 25개인 방에서 방 상태와 50명분의 내 정보를 만드는 데 DB 조회 4번(방, 참여자, 메뉴, 그룹), 약 13ms가 걸렸다(로컬 Testcontainers MySQL에서 6번 측정). 사람이 늘어도 조회 횟수는 같다.
- 테스트로 확인: 방장 연결에는 손님이 낸 메뉴가, 손님 연결에는 방장이라는 사실이 오지 않는다.
- 실제 서버로 확인: 손님 연결로 받은 이벤트 전체에 `"host":true`가 한 번도 없었다.

1. 글자가 정확히 같을 때만 같다고 본다. 가장 단순하지만 띄어쓰기 하나로 표가 갈린다.
2. 비교할 때만 이름을 다듬는다: 유니코드 정규화(NFKC) → 모든 공백 제거 → 소문자로 바꾸기. 화면에 보이는 이름은 그대로 둔다.
3. 글자가 조금 달라도 비슷하면 묶는다(글자 몇 개가 다른지 세는 방법 등). "제육"과 "제육볶음"은 묶을 수 있지만 "라면"과 "라멘"처럼 다른 메뉴도 묶는다.

**선택과 이유**: 2번. 띄어쓰기와 대소문자 말고도, 모양이 같은데 컴퓨터 안의 글자 코드가 다른 경우까지 막는다.
- NFKC: 전각 문자 "ＰＩＺＺＡ"와 "PIZZA"처럼 모양이 같은 글자를 하나로 맞춘다.
- 공백: 일반 띄어쓰기뿐 아니라 줄바꿈 없는 공백(U+00A0) 같은 특수한 공백도 지운다.
- 소문자: 기기 언어 설정에 따라 결과가 달라지지 않게 `Locale.ROOT`를 쓴다.
- 3번처럼 의미가 비슷한 메뉴를 묶는 것은 기능 6의 AI가 할 일이다.

**결과**: `SameNameMenuGrouperTest`로 확인한다. "할매집 제육"과 "제육"은 묶지 못한다(알려진 한계, 기능 6에서 해결).

## 30. 동시에 답할 때 (잠금 실험)

- 날짜: 2026-11-26
- 고른 사람: Claude가 고름

**문제**: 그룹 사람들이 거의 동시에 답하면 결과가 제대로 나올까. 각 요청은 자기 답을 쓴 뒤 "모두 답했나?"를 확인해서, 모두 답했으면 결과를 낸다.

**고려한 선택지**

1. 지금까지처럼 방을 잠그고(`SELECT ... FOR UPDATE`) 처리한다. 같은 방의 요청이 한 명씩 차례로 처리된다.
2. 잠그지 않는다. 각자 다른 행(자기 답)만 고치므로 충돌하지 않을 것 같지만, "모두 답했나?"는 다른 사람의 행을 읽어야 한다.

**선택과 이유**: 1번. 실험해 보니 2번은 결과가 아예 나오지 않았다.

**결과**
- 답하기에서 방 잠금을 잠깐 빼고 "20명이 동시에 동의" 테스트를 8번 돌렸더니 8번 모두 실패했다. 20명이 모두 답했는데도(답한 사람 20/20) 그룹이 "답 기다리는 중"으로 남았고, 메뉴 20개가 하나도 합쳐지지 않았다.
- 이유: 각 요청이 "모두 답했나?"를 확인하는 순간에는 다른 요청의 답이 아직 커밋되지 않아서 보이지 않는다. 그래서 모두가 "아직 다 안 답했다"고 판단하고, 아무도 결과를 내지 않았다.
- 잠금을 넣으면 마지막 사람이 앞사람들의 답을 모두 본 뒤 결과를 낸다. 20명 동시 동의는 바로 한 번 합쳐졌고, 50명이 동시에 "합치기 끝냄"을 눌러도 투표 단계로 한 번만 넘어갔다.

## 31. 직접 합치기의 대표 메뉴 (서비스 규칙 변경)

- 날짜: 2026-11-26
- 고른 사람: 직접 (아이디어). Claude는 장단점을 따져 보고 찬성함

**문제**: 원래 규칙은 "직접 합치기도 두 메뉴 중 무작위로 대표를 정한다"였다. 그런데 직접 요청에는 요청한 쪽과 요청받은 쪽이 있다.

**고려한 선택지**

1. 두 메뉴 중 무작위로 대표를 정한다. (원래 규칙, 자동 그룹과 같음)
2. 요청받은 메뉴가 대표로 남고, 요청한 메뉴가 거기에 합쳐진다.
3. 요청할 때 요청한 사람이 방향("내 메뉴에 합쳐 주세요"/"그 메뉴에 합칠게요")을 고른다. 자유롭지만 규칙과 화면이 복잡해진다.

**선택과 이유**: 2번.
- 요청의 뜻과 맞다. 직접 요청은 "제 메뉴를 저 메뉴에 합쳐 주세요"라는 뜻이라, 요청한 사람이 자기 메뉴를 내려놓겠다고 먼저 나선 것이다.
- 요청받은 사람이 동의하기 쉽다. 무작위면 동의했다가 내 메뉴(예: "할매집 제육")가 사라질 수 있어서 거절하기 쉽다. 2번이면 요청받은 사람은 잃는 게 없어서, 합치기가 더 잘 되고 표가 덜 갈린다.
- 이미 합쳐진 메뉴가 흔들리지 않는다. 여러 명이 합쳐 놓은 메뉴에 누가 요청했을 때, 무작위면 대표가 요청한 사람 메뉴로 바뀔 수 있다. 먼저 합친 사람들은 그 결정에 끼지도 못했다.
- 결과를 미리 알 수 있어서, 보내기 전에 "받아들여지면 내 메뉴는 '△△'에 합쳐져요"라고 보여줄 수 있다.

**대가**
- 자동 그룹(무작위)과 규칙이 다르다. 자동 그룹은 먼저 요청한 사람이 없고, 직접 요청은 요청한 쪽이 있으니 다른 게 맞다고 봤다.
- 자기 메뉴를 지키고 싶은 사람은 먼저 요청하지 않고 기다릴 수 있다. 그래도 무작위일 때 요청받은 사람이 거절하는 것보다는 낫다.
- 결과를 보면 어느 메뉴 쪽이 요청했는지 알 수 있다(누구인지는 모른다).

**결과**: 요청을 받아들이면 난수와 상관없이 항상 요청받은 메뉴가 남는 것을 `MergeGroupTest`와 `DirectMergeApiTest`로 확인한다.

## 33. "요청할 수 있는가" 규칙을 한곳에

2. 서버만 검사하고, 화면은 모든 메뉴에 버튼을 보여준다. 누르면 그제야 에러로 알려 준다.
3. 화면도 방 상태를 보고 같은 규칙을 계산한다. 규칙이 Java와 TypeScript 두 곳에 생겨서 어긋날 수 있다.

**선택과 이유**: 1번. 화면에서 켜진 버튼을 눌렀는데 서버가 거절하는 식으로 둘이 어긋나지 않는다. 규칙은 DB 없이 단위 테스트로 하나씩 확인할 수 있다(`MergeRequestRulesTest`).

**대가**: "합치기 끝냄"을 누른 사람의 메뉴는 버튼이 꺼지므로, 그 메뉴의 제안자가 끝냈다는 것은 보인다(누구인지는 안 보인다). 끝낸 사람의 메뉴에 요청할 수 없다는 규칙 자체에서 오는 것이라 받아들였다.

**고려한 선택지**

**선택과 이유**: 1번. 쓰는 쪽이 단순하고 기록이 남는다. 남아 있는 메뉴끼리만 합칠 수 있어서 고리가 생기지 않는다. 메뉴는 방마다 한 번에 다 읽어 두므로 따라가는 데 DB 조회가 늘지 않는다.

## 35. 동시에 요청할 때 (잠금 실험)

| 투표의 "다 좋음"도 되돌릴 수 없다 | 제안 단계의 "다 좋음"은 되돌릴 수 있었지만, 투표는 "제출 후 변경 불가"라 같은 규칙으로 맞췄다. 대신 누르기 전에 확인 창을 띄운다(확인 창은 52번에서 없애고 안내 문구로 바꿨다) | Claude 제안, 승인 |
| 표를 하나도 못 받은 메뉴는 0점이다 | "덜 싫은 메뉴로 정한다"는 규칙을 그대로 따른 결과다. 다른 메뉴가 모두 마이너스면 표를 못 받은 메뉴가 결정될 수 있다 | Claude 제안, 승인 |
| 0표로는 제출할 수 없다 | 안 찍으려면 "다 좋음"을 누른다. 두 가지 길이 같은 뜻이면 헷갈린다 | Claude가 정함 |
| 메뉴가 결정된 뒤에는 새로 들어올 수 없다 | "투표가 끝나기 전이면 참여할 수 있다"는 원래 규칙을 따랐다. 이미 참여한 사람은 다시 들어와 결과를 볼 수 있다 | Claude가 정함 |
| 같은 투표지를 다시 보내면 그대로 성공(200), 다른 내용이면 거절(409) | 합치기 답(24번)과 같은 방식. 버튼 두 번 누르기나 느린 네트워크에서 다시 보내기가 에러로 보이지 않게 한다 | Claude가 정함 |

## 38. 투표 저장 구조

- 날짜: 2026-11-26
- 고른 사람: Claude가 고름

**문제**: 사람마다의 투표(표 1~2개 또는 "다 좋음")를 어떻게 저장할까. 동점일 때의 재투표(기능 5)도 같은 방식으로 다뤄야 한다.

**고려한 선택지**

1. `ballot`(투표지: 누가, 몇 번째 판에, "다 좋음"인지) + `vote`(표: 어느 메뉴에, +1/-1) 두 테이블
2. 참여자 테이블에 "1번 표 메뉴, 1번 표 점수, 2번 표 메뉴, 2번 표 점수" 칼럼을 둔다. 테이블은 적지만, 재투표 때 칼럼이 또 늘고 "메뉴별로 세기"가 복잡해진다.
3. 표 테이블 하나에 (누가, 메뉴, 점수)만 둔다. 단순하지만 "다 좋음"을 저장할 곳이 없고, "제출했는지"를 표가 있는지로만 알 수 있다.

**선택과 이유**: 1번. 투표지가 "냈다"는 사실(다 좋음 포함)을 나타내고, 표는 투표지에 딸린다. 재투표는 `vote_round = 2`인 투표지로 저장하면 된다.

**DB가 막아 주는 규칙**
- 한 사람이 한 판에 투표지 하나: `UNIQUE (participant_id, vote_round)`
- 한 투표지에서 한 메뉴에 1표: `UNIQUE (ballot_id, menu_id)`
- 점수는 +1 또는 -1: `CHECK (point IN (-1, 1))`
- "최대 2표"는 행 개수에 대한 규칙이라 CHECK로 표현할 수 없어서, 앱이 방을 잠근 상태에서 지킨다.

**같이 정한 것**: "끝냈는지" 기준(28번)에 투표지를 더했다. `Participant.hasFinished(단계, 내 메뉴, 내 투표지)` 하나로 제안·합치기·투표의 "끝냄"을 모두 판단한다.

## 39. 같은 사람이 동시에 투표할 때 (잠금 실험)

- 날짜: 2026-11-26
- 고른 사람: Claude가 고름

**문제**: 같은 사람이 투표지를 거의 동시에 여러 번 보내면(탭 여러 개, 빠른 두 번 누르기) 어떻게 될까. DB에 UNIQUE가 있으니 잠금이 없어도 되지 않을까?

**결과**
- 투표 API에서 방 잠금을 잠깐 빼고, 같은 사람이 서로 다른 투표지 10개를 동시에 보내는 테스트를 5번 돌렸다. 5번 모두 투표지는 1장만 저장됐다. DB의 UNIQUE가 마지막에 막아서 데이터는 지켜졌다.
- 하지만 나머지 9개는 "이미 투표했습니다"(409)가 아니라 DB 에러(`DataIntegrityViolationException`)로 끝났다. 사용자에게는 서버 오류(500)로 보인다. 각 요청이 "이미 냈나?"를 확인할 때는 아무도 아직 커밋하지 않아서 모두 "안 냈다"고 보고 저장하려 했기 때문이다.
- 잠금을 넣으면 한 명씩 차례로 처리돼서, 1개만 저장되고 9개는 409로 깔끔하게 거절된다.
- 정리: DB 제약은 "데이터가 틀리지 않게" 하는 마지막 안전장치이고, 잠금은 "사용자에게 맞는 답을 주게" 한다. 둘 다 둔다.

## 41. 결정된 이름과 결정 이유 저장

- 날짜: 2026-11-27
- 고른 사람: Claude가 고름

**문제**: 랜덤 선택에서 뽑힌 사람이 정한 이름은 메뉴 목록에 없을 수 있어서, 결정된 메뉴를 가리키는 `result_menu_id`(기능 4)로는 담을 수 없다. 또 결과 화면에 "어떻게 정해졌는지"를 보여줘야 한다.

**고려한 선택지**

1. `room`에 `result_name`(결정된 이름)과 `result_reason`(결정 이유)을 더한다. `result_menu_id`는 메뉴 중에서 정해졌을 때만 채운다.
2. 뽑힌 사람이 정한 이름을 메뉴(`menu` 행)로 새로 만들어 `result_menu_id`로 가리킨다. 그런데 메뉴는 "참여자가 제안한 것"이라(한 사람에 하나, `UNIQUE (participant_id)`) 뽑힌 사람이 이미 메뉴를 냈으면 넣을 수 없고, 제안하지 않은 메뉴가 목록에 섞인다.
3. 이유는 저장하지 않고 그때그때 계산한다(재투표 투표지가 있는지 등). 그런데 "재투표에서 1등이 하나라서"와 "또 동점이라 무작위로"는 난수 결과라 나중에 다시 계산할 수 없다.

**선택과 이유**: 1번. 결정하는 순간에 이름과 이유를 함께 저장하므로 화면은 읽기만 하면 된다. 이유는 ONLY_MENU(메뉴가 하나) / VOTE(투표) / REVOTE(재투표) / REVOTE_RANDOM(재투표 후 무작위) / PICKED(뽑힌 사람이 정함)다. "지금 몇 번째 판인지"(`Room.voteRound()`)도 단계와 결정 이유로 알 수 있어서 따로 저장하지 않는다.

**결과**: 이미 끝난 방(기능 4에서 만든 방)도 V6에서 채운다. 기능 4에는 재투표와 랜덤 선택이 없었으므로, 투표지가 있으면 투표로, 없으면 메뉴가 하나라서 정해진 것이다. `V6MigrationTest`로 확인한다(46번).

## 42. 뽑기 차례 저장 구조

- 날짜: 2026-11-27
- 고른 사람: Claude가 고름

**문제**: 랜덤 선택에서 서버는 누가 뽑혔는지, 지금 몇 번째 차례인지(두 번 누르기 막기, 43번), 이번 바퀴에 누가 이미 뽑혔는지(다시 안 뽑기, 40번)를 알아야 한다. 누가 뽑혔는지는 다른 참여자에게 절대 보이면 안 된다.

**고려한 선택지**

1. `pick_turn` 테이블: 한 명을 뽑을 때마다 한 줄(누구, 몇 번째 차례, 몇 번째 바퀴, 상태, 정한 이름).
2. `room`에 "지금 뽑힌 사람"과 "차례 번호" 칸만 둔다. 단순하지만 지난 차례를 몰라서 "이번 바퀴에 이미 뽑힌 사람"을 알 수 없다.
3. `participant`에 "이번 바퀴에 뽑혔음" 표시를 둔다. 바퀴가 바뀔 때마다 모두 지워야 하고, 기록이 남지 않는다.

**선택과 이유**: 1번. 지난 차례가 남아서 바퀴 계산이 쉽고, 나중에 "몇 번 만에 정해졌나" 같은 것도 볼 수 있다. 상태는 ACTIVE(정하는 중) / DECIDED(정함) / EXPIRED(시간 초과) / SKIPPED(방장이 다른 사람을 뽑음)다.

**DB가 막아 주는 규칙**
- 같은 방에서 같은 차례 번호는 한 번: `UNIQUE (room_id, turn_number)`
- 방마다 정하는 중인 차례는 하나: MySQL에는 "조건이 맞는 행끼리만 UNIQUE"(부분 인덱스)가 없다. 그래서 정하는 중일 때만 방 번호가 들어가는 칸(`active_room_id`, DB가 계산하는 생성 칼럼)을 만들고 거기에 UNIQUE를 건다. NULL끼리는 UNIQUE에 걸리지 않으므로 끝난 차례는 몇 개든 괜찮다. 정하는 중인 차례를 하나 더 넣으면 DB가 거절하는 것을 `RandomPickTest`로 확인한다.

**같이 확인한 것: flush 순서**
- 다시 뽑을 때는 지난 차례를 끝내는 UPDATE가 새 차례를 넣는 INSERT보다 먼저 DB에 가야 위 규칙에 걸리지 않는다. 그래서 새 차례를 넣기 전에 `flush()`를 부르게 했다.
- 실험: `flush()`를 빼고 랜덤 선택 테스트 15개를 돌려도 모두 통과했다. SQL 로그를 보니, 새 차례를 뽑기 전에 지난 차례들을 조회하는 쿼리 바로 앞에서 Hibernate가 UPDATE를 먼저 보냈다. 같은 테이블을 조회하기 전에는 바뀐 내용을 먼저 반영하는 자동 flush 때문이다.
- 그래도 `flush()`는 남겼다. 조회 순서가 바뀌면(예: 지난 차례를 조회하지 않게 고치면) 조용히 깨지는 숨은 의존이라, 순서가 필요하다는 것을 코드에 드러냈다.

## 43. "다른 사람 뽑기" 두 번 누르기 막기

- 날짜: 2026-11-27
- 고른 사람: Claude가 고름

**문제**: 방장 버튼은 화면에 보이던 단계(`from`)를 함께 보내서, 이미 넘어갔으면 거절하는 방식으로 두 번 누르기를 막았다(20번). 그런데 랜덤 선택에서는 다시 뽑아도 단계가 그대로라, `from`만으로는 두 번째 누름을 알아챌 수 없다. 그대로 두면 두 번 누를 때 두 번 다시 뽑힌다.

**고려한 선택지**

1. 화면에 보이던 뽑기 차례 번호(`pickTurn`)도 함께 보내고, 지금 차례와 다르면 거절(409)한다. `from`과 같은 방식이다.
2. 다시 뽑은 뒤 몇 초 동안은 다시 못 뽑게 한다. 몇 초로 할지가 임의적이고, 느린 네트워크에서는 맞지 않는다.
3. "다른 사람 뽑기"를 따로 API로 만든다(`/pick-turns/{번호}/skip` 같은). 같은 일을 하지만 API가 하나 늘고, 화면의 "다음 단계로" 버튼과 따로 놀게 된다.

**선택과 이유**: 1번. 기존 방식에 칸 하나만 더하면 된다. 차례 번호는 원래 모두에게 보이는 정보("몇 번째 뽑기")라 새로 드러나는 것이 없다.

**결과**: 같은 차례 번호로 두 번 보내면 두 번째는 409(`PHASE_ALREADY_CHANGED`)다. 두 요청을 동시에 보내도 방 잠금 덕분에 하나만 성공하고 하나는 409다(`RandomPickTest`).

## 44. 정하는 순간 시간이 다 될 때 (잠금 실험)

- 날짜: 2026-11-27
- 고른 사람: Claude가 고름

**문제**: 뽑힌 사람이 메뉴를 정하는 요청과 타이머의 "시간 초과로 다시 뽑기"가 거의 동시에 일어나면 어떻게 될까. 둘 중 하나만 일어나야 한다.

**결과**
- 정하기 API에서 방 잠금을 잠깐 빼고 "정하기와 시간 초과를 동시에" 실험을 20번 돌렸더니, 20번 모두 둘 다 일어났다. 방은 결정(FINISHED)됐는데 다른 사람이 또 뽑혀서, 끝난 방에 "정하는 중"인 차례가 남았다. 두 요청이 같은 "정하는 중인 차례"를 동시에 읽고 각자 처리했기 때문이다(30번과 같은 이유).
- DB 규칙(정하는 중인 차례 하나, 42번)도 이것을 막지 못했다. 한쪽은 그 차례를 "정함"으로, 다른 쪽은 "시간 초과"로 바꾸고 새 차례를 하나만 넣어서, 정하는 중인 차례는 여전히 하나였다. DB 규칙은 "정해진 방에는 정하는 중인 차례가 없다"까지는 알지 못한다.
- 잠금을 넣으면 둘이 차례로 처리된다. 같은 실험을 10번 반복하는 테스트(`RandomPickTest`)에서 매번 "정해졌으면 다시 안 뽑힘" 또는 "다시 뽑혔으면 정해지지 않음(뽑힌 사람이 아니라고 거절)" 중 하나만 일어난다.

## 45. 같은 클래스 안에서 부르면 @Transactional이 안 걸린다 (실수에서 배운 것)

- 날짜: 2026-11-27
- 고른 사람: Claude가 고름

**문제**: "다른 사람 뽑기"에 차례 번호가 필요해져서 `advanceByHost(code, token, from, pickTurn)`을 만들고, 기존 호출을 위해 인자 3개짜리를 남겨 4개짜리를 부르게 했다. 그러자 테스트 15개가 "No active transaction"으로 실패했다.

**원인**: `@Transactional`은 Spring이 객체 앞에 끼워 넣은 대리 객체(프록시)가 처리한다. 밖에서 부르면 프록시를 거쳐 트랜잭션이 열리지만, 같은 클래스 안에서 `this.advanceByHost(...)`처럼 부르면 프록시를 거치지 않아서 4개짜리에 붙은 `@Transactional`이 무시된다. 그래서 트랜잭션 없이 방을 잠그려다(`SELECT ... FOR UPDATE`) 실패했다.

**고려한 선택지**

1. 3개짜리에도 `@Transactional`을 붙인다. 바로 고쳐지지만 같은 함정이 코드에 남는다.
2. 3개짜리를 없앤다. 부르는 곳이 테스트뿐이었다.

**선택과 이유**: 2번. 운영 코드에 테스트만 쓰는 메서드를 두지 않고, 함정 자체를 없앤다. 테스트는 인자 4개짜리에 `null`(랜덤 선택이 아니라 차례 번호가 필요 없음)을 넘긴다.

**기억할 것**: 같은 클래스의 메서드끼리 부를 때는 `@Transactional`, `@Async`, `@Cacheable`처럼 프록시로 동작하는 기능이 걸리지 않는다.

## 46. 기존 데이터를 새 규칙에 맞게 옮기기 (V6)

- 날짜: 2026-11-27
- 고른 사람: Claude가 고름

**문제**: 기능 4에서는 재투표와 랜덤 선택이 자리만 있어서, 그 단계로 간 방에는 타이머도 뽑힌 사람도 없다. 새 코드는 "랜덤 선택 중이면 정하는 중인 차례가 하나 있다"고 믿는다. 그래서 그런 방은 타이머가 없어 영원히 그대로이고, 아무도 정할 수 없고, 방장의 "다른 사람 뽑기"는 서버 오류(500)가 난다. 로컬 DB에 실제로 그런 방이 2개 있었다.

**고려한 선택지**

1. V6에서 두 단계가 지금 막 시작된 것처럼 옮긴다. 재투표 중인 방은 투표 시간만큼 타이머를 걸고, 랜덤 선택 중인 방은 참여자 한 명을 뽑아 첫 차례를 만들고 타이머를 건다.
2. 코드가 "차례가 없는 랜덤 선택"도 처리하게 한다. 한 번만 필요한 예외 처리가 코드에 계속 남는다.
3. 아직 배포 전이니 옮기지 않는다. 하지만 마이그레이션은 어느 DB에서 돌려도 맞아야 한다.

**선택과 이유**: 1번. 시각은 앱과 같이 UTC로 넣는다(`UTC_TIMESTAMP()`). `NOW()`는 DB 시간대 설정을 따르므로 한국 시간으로 들어갈 수 있다.

**결과**
- `V6MigrationTest`: 테스트 전용 MySQL을 따로 띄워 V5까지 올리고, 기능 4 시절의 방 6개(투표로 끝남, 메뉴 하나로 끝남, 랜덤 선택 중, 재투표 중, 투표 중, 대기 중)를 넣은 뒤 V6을 올려서 확인한다.
- 옮기는 SQL을 빼고 돌리면 4개 테스트 중 2개(랜덤 선택, 재투표)가 실패한다. 테스트가 실제로 잡아낸다는 뜻이다.
- 다른 통합 테스트는 빈 DB에 V6까지 한 번에 올린다. 이 테스트가 없으면 옮기는 SQL은 한 줄도 실행되지 않은 채로 모든 테스트가 통과한다.
- 로컬 DB에서 멈춰 있던 방 2개는 첫 차례가 생겼고, 1분 뒤 시간 초과로 다른 참여자가 다시 뽑혔다.

**실수와 교훈**: 이 SQL은 V6을 로컬 DB에 한 번 적용한 뒤에 추가했다. Flyway는 이미 적용한 파일이 바뀌면(체크섬이 다르면) 실행을 거부한다. V6은 아직 커밋 전이라 로컬 DB에서만 V6을 손으로 되돌리고(빈 `pick_turn` 테이블과 새 칸 2개 삭제, 이력 한 줄 삭제) 다시 적용했다. 머지된 뒤라면 V6은 절대 고치지 않고 V7을 새로 만들어야 한다.

## 47. 모두 뽑힌 뒤에는 자동으로 다시 뽑지 않기 (서비스 규칙 변경)

- 날짜: 2026-11-27
- 고른 사람: 직접 (Claude 추천안을 고름)

**문제**: 40번 규칙대로면 시간이 다 될 때마다 다시 뽑고, 한 바퀴를 다 돌면 처음부터 다시 뽑는다. 그래서 모두 창을 닫은 방도 다시 뽑기를 끝없이 하고, 뽑을 때마다 `pick_turn`에 한 줄이 쌓인다. 랜덤 선택 시간이 1분이면 방 하나에 하루 1,440줄이다. 랜덤 선택은 아무도 고르지 않은 방에서 열리는 단계라, 사람들이 그냥 나가 버린 방이 특히 여기에 남기 쉽다.

**확인**: 로컬 DB에서 기능 4 시절에 멈춰 있던 방 2개(46번)가 V6으로 옮겨진 뒤, 약 3시간 반 동안 135줄씩 쌓였다.

**고려한 선택지**

1. 한 바퀴를 다 돌면 자동 다시 뽑기를 멈춘다. 마지막에 뽑힌 사람은 시간 제한 없이 정할 수 있고, 방장은 계속 "다른 사람 뽑기"를 할 수 있다.
2. 지금처럼 계속 다시 뽑고, 배포 전에 "오래된 방 지우기"를 따로 만든다. 방이 지워지기 전까지는 계속 쌓인다.
3. 몇 바퀴 뒤에는 서버가 남은 메뉴 중 무작위로 정하고 끝낸다. 아무도 제안하지 않은 방은 고를 메뉴가 없어서 "결정 없이 끝남"이라는 새 상태가 필요하다.

**선택과 이유**: 1번.
- 사람이 있는 방에서는 모두 한 번씩 기회를 받는 것까지 그대로이고, 버려진 방만 조용히 멈춘다.
- 쌓이는 줄이 "참여자 수 × 방장이 누른 횟수"로 묶인다. 방장마저 없으면 그 방은 더 아무 일도 하지 않는다(대기 중에 버려진 방과 같다).
- 새 단계나 새 칸이 필요 없다. 멈춘 상태는 "랜덤 선택인데 끝나는 시각이 없음"으로 나타나고, 타이머는 끝나는 시각이 있는 방만 보므로 더는 건드리지 않는다.

**결과**
- `RandomPickTest`: 2명 방에서 두 사람 모두 시간 초과 → 차례 2개에서 멈추고 끝나는 시각이 없어진다. 마지막 사람은 그 뒤에도 정할 수 있다. 멈춘 뒤 방장이 누르면 3번째 차례(2바퀴)와 타이머가 생긴다.
- 멈추는 코드를 빼고 돌리면 이 두 테스트가 실패하는 것도 확인했다.
- 로컬 DB의 버려진 방 2개는 새 코드로 다시 띄운 뒤 지금 바퀴를 마저 돌고(한 번씩 더 뽑힘) 136줄에서 멈췄다. 끝나는 시각이 없어졌고, 정하는 중인 차례는 마지막에 뽑힌 사람 것 하나만 남았다.

## 48. 새 바퀴의 첫 사람은 바로 앞 사람과 다르게

- 날짜: 2026-11-27
- 고른 사람: Claude가 고름

**문제**: 47번 뒤로 새 바퀴는 방장이 "다른 사람 뽑기"를 누를 때만 시작된다. 그런데 새 바퀴는 처음부터 전원 중에서 뽑아서, 방금 뽑혔던 사람이 또 뽑힐 수 있다(2명인 방이면 50%). 버튼 이름과 맞지 않고, 2명인 방의 방장은 "다른 사람"이 자기라는 것을 알아서 더 헷갈린다.

**고려한 선택지**

1. 새 바퀴의 첫 뽑기에서만 바로 앞에 뽑힌 사람을 뺀다. 혼자인 방이면 뺄 수 없으니 그 사람을 다시 뽑는다.
2. 그대로 둔다. 같은 사람이 나오면 방장이 한 번 더 누르면 된다.

**선택과 이유**: 1번. 40번의 "처음부터 다시 뽑는다"를 조금 좁히는 것이라 따로 적는다. 바로 앞 사람은 새 바퀴에서 아직 안 뽑힌 사람이므로, 두 번째 뽑기부터는 다시 후보가 된다.

**결과**: `PickTurnTest`에서 확인한다.
- 2명 방은 새 바퀴의 첫 사람이 항상 다른 사람이다.
- 3명 방은 100번 뽑아도 바로 앞 사람이 한 번도 안 나오고, 나머지 두 명은 모두 나온다.
- 혼자인 방은 그 사람이 다시 뽑힌다.
- 빼는 코드를 지우면 100번 테스트가 실패한다. 2명 테스트는 50% 확률로 우연히 통과할 수 있어서 100번 테스트를 따로 뒀다.

## 49. 개발용 여러 명 테스트 화면 (관리자 모드 대신)

- 날짜: 2026-11-27
- 고른 사람: 직접 (관리자 모드를 생각했다가 Claude 추천안을 고름). 칸을 나누는 방법과 칸 수는 Claude가 고름

**문제**: 배포 전에 여러 명이 함께 쓰는 흐름(제안, 합치기, 투표, 랜덤 선택)을 직접 써 보며 확인해야 한다. 그런데 참여자는 브라우저 쿠키로 구분된다. 그래서 한 사람이 여러 참여자를 흉내 내려면 크롬 일반 창, 시크릿 창, 엣지처럼 쿠키를 따로 쓰는 창을 여러 개 띄우고, 방을 만들 때마다 링크를 붙여 넣어야 한다. 번거롭고 실수하기 쉽다.

**고려한 선택지**

| 선택지 | 장점 | 단점 |
|---|---|---|
| 서비스 안의 관리자 모드 (관리자가 다른 참여자 대신 누름) | 한 화면에서 모두 조작한다 | 서버는 토큰의 해시만 저장해서 남의 토큰을 만들 수 없다. 그래서 쿠키 없이 다른 사람으로 처리하는 길을 따로 뚫어야 하고, 이것이 익명 약속을 깨는 뒷문이 된다. 실제 사용자가 쓰는 쿠키와 SSE 길을 건너뛰어 그쪽 버그를 놓친다. 관리자 로그인과 비밀번호 관리까지 기능 하나만큼 크다 |
| 브라우저 창 여러 개 | 코드가 필요 없다 | 쿠키를 따로 쓰는 창을 브라우저와 모드마다 하나씩 열어야 한다(시크릿 창끼리는 쿠키를 같이 써서 한 사람이다). 방마다 링크를 붙여 넣어야 한다 |
| 개발용 여러 명 테스트 화면 (한 탭에 칸 여러 개) | 한 화면에서 여러 명을 조작한다. 칸마다 진짜 쿠키와 SSE를 쓴다. 배포용 빌드에 들어가지 않는다 | 확인 창이 뜨면 답할 때까지 모든 칸이 멈춘다(52번에서 확인 창을 없애서 지금은 해당하지 않는다). 칸 하나만 연결을 끊어 볼 수 없다 |
| 자동 E2E 테스트 (Playwright 등) | 컴퓨터가 여러 명을 대신 눌러서 매번 똑같이 확인한다. CI에서도 돌릴 수 있다 | 화면을 바꿀 때마다 테스트도 같이 고쳐야 한다. 디자인을 개선한 뒤에 만드는 것이 낫다 |

**선택과 이유**: 개발용 여러 명 테스트 화면. "한 화면에서 여러 명 조작"이라는 생각은 살리고, 서비스 안이 아니라 개발 환경에만 둔다. 이 화면은 브라우저 여러 개로 할 수 있는 일을 한 탭에서 할 뿐이라, 일반 사용자가 못 하는 일을 가능하게 하지 않는다.

**칸마다 다른 참여자로 만드는 방법** (Claude가 고름): 한 탭 안의 칸(iframe)은 쿠키를 같이 쓴다. 쿠키를 칸마다 나누는 방법을 비교했다.

| 방법 | 판단 |
|---|---|
| 칸마다 다른 호스트로 띄운다 (`localhost`, `127.0.0.1` 등) | 칸끼리 다른 사이트가 되어, `SameSite=Lax` 쿠키가 iframe 안에서 저장되거나 전송되지 않을 수 있다. 브라우저마다 동작이 다를 수 있다 |
| 개발 중에만 쿠키 대신 헤더로 참여자를 보낸다 | 실제 사용자와 다른 길을 테스트하게 된다. EventSource는 헤더를 붙일 수 없어서 SSE도 따로 바꿔야 한다 |
| **쿠키 경로로 나눈다 (고름)** | 칸 N은 앱을 `/p/N/...` 주소로 띄운다. 개발 서버(Vite)는 `/p/N/api` 요청을 `/api`로 바꿔 백엔드에 넘기고, 돌아오는 쿠키의 경로(`Path=/api/rooms/코드`) 앞에 `/p/N`을 붙인다. 브라우저는 쿠키를 경로마다 따로 보관하므로 칸마다 다른 참여자가 된다. 모두 같은 주소라 SameSite 문제가 없고, 백엔드는 바뀌지 않는다 |

**칸 수: 4개까지** (Claude가 고름): HTTP/1.1에서 브라우저는 한 주소에 연결을 6개까지만 연다. 칸마다 SSE가 연결 하나를 계속 쓰므로, 칸이 많으면 제안이나 투표 요청이 쓸 연결이 모자라다. 화면 없는 크롬에서 칸 수를 늘려 가며 방장의 "시작" 요청이 처리되는 시간을 쟀다.

| 칸 수 | "시작" 요청 |
|---|---|
| 4개 | 154ms 만에 처리 |
| 5개 | 177ms 만에 처리 |
| 6개 | 8초가 지나도 처리되지 않음. 칸 하나를 닫자 138ms 만에 처리 |

5개도 되지만 남는 연결이 하나뿐이라, 같은 크롬에서 앱 탭을 하나만 더 열어도 막힌다. 그래서 여유를 두고 4개로 정했다. 배포에서 HTTPS와 HTTP/2를 쓰면 연결 하나로 여러 요청을 함께 보내서 이 한도가 사라진다. 배포 계획에서 함께 다룬다.

**배포용 빌드에 들어가지 않게 하기**
- 테스트 화면은 `dev-board.html`이라는 따로 된 시작 파일이다. 배포용 빌드는 `index.html`만 만들기 때문에 들어가지 않는다.
- 앱 쪽의 칸 주소 처리(`src/devPanel.ts`)는 `import.meta.env.DEV`가 거짓인 배포용 빌드에서 코드째 빠진다.
- CI가 배포용 빌드에 `dev-board.html`과 칸 주소 처리 코드(정규식 `p\/\d+`)가 없는지 검사한다. 개발 모드로 일부러 빌드해 보니 이 검사가 정규식을 찾아냈다. 검사가 헛돌지 않는다는 뜻이다.

**결과**: 화면 없는 크롬으로 테스트 화면을 처음부터 끝까지 눌러 봤고, 25개 항목이 모두 통과했다.
- 칸 4개로 들어가면 참여 인원 4명이다. 쿠키는 `/p/1/api/rooms/코드`부터 `/p/4/...`까지 4개이고, 값이 모두 다르며 HttpOnly와 SameSite=Lax가 그대로다.
- 방장 표시와 "시작"은 칸 1에만 있다. 제안, 합치기, 투표, 결정이 모든 칸에 실시간으로 반영된다.
- 칸 새로고침, 닫았다가 다시 들어가기, 테스트 화면 새로고침 모두 같은 참여자로 돌아온다.
- 칸 밖의 원래 앱(`/api`)도 그대로 동작한다.

**알게 된 것**: 체크리스트([manual-test.md](manual-test.md))를 만들면서 테스트 화면으로 미리 해 보다가 문제 하나를 찾았다. 백엔드를 다시 켜도 화면이 멈춰 있는 문제로, 그 문서의 "찾은 문제" 1번이다. 고칠 때 따로 기록한다. 그 밖에 두 가지를 배웠다.
- 개발자 도구의 "오프라인"으로는 이미 열린 SSE 연결이 끊기지 않는다. 그래서 연결 끊김은 서버를 껐다 켜서 확인한다.
- 방장이 "다음 단계로"를 더블클릭하면 두 단계가 넘어가는 것처럼 보였는데, 실험 방법의 착오였다. 자동화 도구(Playwright)의 `click()`은 두 번째 클릭 때 바뀐 화면에서 버튼을 다시 찾아서 누른다. 사람의 더블클릭은 같은 화면 좌표를 두 번 누른다. 같은 좌표를 누르게 고쳐서 다시 재니, 화면 크기 2가지와 클릭 간격 100ms, 250ms 모두에서 한 단계만 넘어갔다. 새 화면에서는 버튼 위치가 달라지기 때문이다. 테스트 도구가 사람과 다르게 움직이면 없는 버그를 만들어 낼 수 있다.

## 50. 단계 시간 기본값과 "제한 없음" (서비스 규칙 변경)

- 날짜: 2026-11-27
- 고른 사람: 직접 (기본 시간, "제한 없음"을 사용자에게도 주기, 모두 끝내면 자동으로 넘기기 유지). 용어와 저장 방식은 Claude가 고름

**문제**: 직접 테스트를 해 보니 기본 1분(체크리스트는 30초)이 혼자 칸 여러 개를 누르기에는 너무 짧았다. 실제 모임에서도 메뉴를 떠올리고 합치기를 의논하기에 1분은 빠듯하다. 시간에 쫓기지 않고 진행하고 싶은 방도 있다.

**정한 것**
1. **기본 시간** (직접): 제안 5분, 합치기 5분, 투표 5분(재투표도 같음), 랜덤 선택 1분이다. 랜덤 선택은 한 사람만 정하면 되고, 뽑힌 사람이 자리에 없을 때 빨리 다음 사람에게 넘어가야 해서 짧게 둔다.
2. **"제한 없음"** (직접): 단계마다 30초~10분 말고 "제한 없음"도 고를 수 있다.
   - 제한 없는 단계는 시간이 다 되는 일 없이, 모두 끝내거나 방장이 넘길 때만 넘어간다.
   - 랜덤 선택이 제한 없음이면 자동으로 다시 뽑지 않는다. 다시 뽑기는 방장의 "다른 사람 뽑기"로만 한다.
   - 개발할 때 여유 있게 테스트하는 데도 이 선택지를 쓴다. 테스트 화면에는 이 값으로 방을 바로 만드는 "빠른 방 만들기" 버튼을 뒀다.
3. **모두 끝내면 자동으로 넘기기는 그대로** (직접, 다시 확인함): 방장에게 알리고 방장이 넘기게 하는 방법도 검토했다. 하지만 그러면 "제한 없음" 단계에서 방장이 나가 버린 방은 영영 멈춘다.

**용어** (Claude가 고름): "제한 없음".
- 시간 목록에서 "10분" 다음에 자연스럽게 읽히고, 진행 중에는 남은 시간 자리에 "시간 제한 없음"으로 보인다.
- "무제한"보다 깔끔한 말을 원해서 다른 후보도 봤다. "끝까지"는 뜻이 흐리다. "방장이 넘길 때까지"는 길고, 모두 끝내도 넘어간다는 점이 빠진다.

**"제한 없음"을 나타내는 방법** (Claude가 고름)

| 방법 | 장점 | 단점 |
|---|---|---|
| **0초 (고름)** | API, 서버 코드, DB가 모두 같은 값을 쓴다. 0초짜리 단계는 원래 없어서 다른 뜻과 헷갈리지 않는다. Java에서도 흔한 약속이다(`URLConnection.setConnectTimeout(0)`은 "무한히 기다림") | 숫자에 특별한 뜻을 붙인다. 그래서 코드에서 0을 직접 비교하지 않게 `NO_LIMIT` 상수와 `proposalLimit()` 같은 메서드로 감쌌다 |
| DB와 API 모두 null | "값이 없음 = 제한 없음"으로 읽힌다 | API에서 이미 "안 보냄(null) = 기본값"으로 쓰고 있어서 둘을 구분할 수 없다. 칸을 빼먹은 요청이 조용히 "제한 없음"이 될 수 있다 |
| 단계마다 칸을 하나 더 둔다 (`proposalNoLimit: true`) | 뜻이 가장 분명하다 | 단계마다 칸이 둘씩 늘고, "300초인데 제한 없음" 같은 모순된 값을 막는 검사가 더 필요하다 |

**DB**
- V7에서 CHECK 규칙을 "0이거나, 30~600 사이 30초 단위"로 바꿨다. 기존 방의 값은 새 규칙에도 맞아서 옮길 데이터가 없다.
- 제한 없는 단계는 끝나는 시각(`phase_ends_at`)을 비워 둔다. 그래서 1초마다 끝나는 시각이 지난 방을 찾는 타이머가 아예 건드리지 않는다.

**화면에서 구분할 것**: 랜덤 선택에서 끝나는 시각이 없는 경우가 둘이 됐다.
- 방장이 "제한 없음"으로 정한 방
- 시간 제한이 있었지만, 모두 한 번씩 뽑혀서 자동 다시 뽑기를 멈춘 방(47번)

안내 문구가 달라야 해서 단계별 시간(`randomPickSeconds`가 0인지)으로 둘을 구분한다.

**결과**
- 백엔드 테스트 242개가 통과했고, 그중 8개가 새로 추가한 것이다. 확인한 내용은 다음과 같다.
  - 기본값이 맞는지
  - 0은 받고 잘못된 값은 서버와 DB 둘 다에서 막는지
  - 제한 없는 단계는 하루가 지나도 그대로이고, 모두 끝내거나 방장이 넘기면 넘어가는지
  - 제한 없는 랜덤 선택은 자동으로 다시 뽑지 않고, 방장이 누를 때만 다시 뽑는지
  - API 응답에 서버 코드의 도우미 메서드가 섞이지 않는지
- 화면 없는 크롬으로 24개 항목을 확인했다.
  - 방 만들기 화면의 기본값과 "제한 없음"
  - 진행 중의 "시간 제한 없음" 표시
  - 빠른 방 만들기
  - 제한 없는 랜덤 선택의 문구, 그리고 시간 있는 랜덤 선택의 문구가 그대로인지

## 52. 확인창 없애기 (서비스 규칙 변경)

- 날짜: 2026-11-27
- 고른 사람: 직접 (확인창 없애기). 랜덤 선택을 "고르기 → 정하기"로 나눈 것은 Claude가 제안하고 직접 OK 함. 두 번 누르기 막기는 Claude가 만들다가 더함

**문제**: 직접 테스트를 해 보니 확인창이 자주 떴다. 확인창은 5곳에 있었다: 투표 "제출", 투표 "다 좋음", 직접 합치기 요청, 랜덤 선택의 정하기, 방장의 "다른 사람 뽑기".
- 확인창이 자주 뜨면 읽지 않고 "확인"을 누르게 된다. 막아 주는 효과는 없고 귀찮기만 하다.
- 일관성도 없었다. "합치기 끝냄", 자동 그룹 답, 방장의 "다음 단계로"도 되돌릴 수 없는데 확인창이 없었다.
- 브라우저 기본 확인창(`window.confirm`)은 휴대폰에서 시스템 경고처럼 보인다.

**고려한 선택지**

| 선택지 | 장점 | 단점 |
|---|---|---|
| 그대로 둔다 | 실수로 누르는 것을 막는다 | 위의 문제가 그대로다 |
| 모두 없앤다 | 깔끔하다 | 랜덤 선택은 메뉴마다 "이걸로 정하기"가 줄지어 있고 누르는 순간 모두의 메뉴가 정해진다. 휴대폰에서 옆 줄을 잘못 누르면 되돌릴 수 없다 |
| **모두 없애고, 랜덤 선택만 고르기와 정하기를 나눈다 (고름)** | 깔끔하고, 한 번 잘못 눌러서 모두의 결과가 정해지는 곳이 없다 | 랜덤 선택에 버튼이 하나 는 것처럼 보인다. 누르는 횟수는 전과 같다(고르기 + 정하기 = 전의 정하기 + 확인) |
| 확인창 대신 몇 초 동안 "되돌리기" (메일의 "보내기 취소"처럼) | 실수를 되돌릴 수 있어서 가장 친절하다 | 서버가 "잠깐 기다리는 표"를 두거나 화면이 보내기를 미뤄야 한다. 모두 끝내면 바로 넘어가는 규칙과도 부딪힌다. 마지막 사람이 내면 바로 다음 단계라 되돌릴 틈이 없다 |
| 버튼을 한 번 더 누르게 한다 ("한 번 더 누르면 제출") | 창이 뜨지 않는다 | 확인창과 같은 귀찮음이 남는다 |

**선택과 이유**
- 랜덤 선택에서는 메뉴의 "고르기"가 입력칸에 이름을 넣기만 하고, "이 메뉴로 정하기"를 눌러야 정해진다. 투표의 "표 고르기 → 제출"과 같은 방식이다. 고른 이름을 고쳐서 정할 수도 있다("짜장면" → "짜장면 곱빼기").
- 직접 합치기의 "이 메뉴에 합치기"도 메뉴마다 줄지어 있다. 하지만 상대가 동의해야 합쳐지므로 그대로 한 번에 보낸다.
- 바꿀 수 없다는 것은 안내 문구에 미리 적는다.
  - 투표: "제출하거나 '다 좋음'을 누르면 바꿀 수 없어요."
  - 직접 합치기: "보낸 요청은 취소할 수 없어요."
- 32번(보낸 요청은 취소할 수 없다)과 37번(투표의 "다 좋음"도 되돌릴 수 없다)의 "대신 확인 창을 띄운다"를 이 결정으로 바꾼다. 49번에 적었던 테스트 화면의 단점("확인 창이 뜨면 모든 칸이 멈춘다")도 사라졌다.

**두 번 누르기 막기** (Claude가 만들다가 더함): 확인창은 "빨리 두 번 누르기"도 막아 주고 있었다. 확인창을 없애면 두 번째 요청이 서버에 간다. 서버는 이미 두 번 받아도 한 번만 처리하지만, 두 번째 요청을 "이미 요청했다"(합치기 요청), "이미 결정됐다"(정하기), "이미 넘어갔다"(다른 사람 뽑기)로 거절한다. 결과는 맞는데 화면에 오류가 보인다.
- 고른 방법: 같은 행동의 답이 오기 전에는 같은 행동을 다시 보내지 않는다(`useRoom`의 `sending`). 한곳만 고치면 모든 버튼에 적용된다.
- 처음에는 답이 오기 전의 모든 요청을 막았다. 그런데 화면 없는 크롬으로 확인하다가, 합치기 질문에 답하고 바로 "합치기 끝냄"을 누르면 두 번째가 소리 없이 무시되는 것을 찾았다. 느린 휴대폰 인터넷에서는 사람도 겪을 수 있다. 그래서 같은 행동만 막고 다른 버튼은 막지 않게 고쳤다.
- 다른 방법: 버튼마다 "보내는 중"이면 누를 수 없게 하기. 누른 것이 보여서 더 친절하지만 버튼마다 고쳐야 한다. 화면 디자인을 손볼 때 함께 하는 것이 낫다.

**결과**: 화면 없는 크롬에서 처음부터 끝까지 진행하는 동안 확인창이 한 번도 뜨지 않았다. "이 메뉴에 합치기"와 "다른 사람 뽑기"를 같은 자리에서 빠르게 두 번 눌러도 요청은 한 번만 갔고, 오류도 보이지 않았다. 합치기 질문에 답하고 바로 "합치기 끝냄"을 눌러도 둘 다 처리됐다.

## 53. 시간 목록 줄이기와 "직접 설정" (서비스 규칙 변경)

- 날짜: 2026-11-27
- 고른 사람: 직접 (목록과 직접 설정). 직접 설정의 단위와 범위(분 단위, 1~60분)는 Claude가 제안하고 직접 OK 함

**문제**: 시간 목록이 30초부터 10분까지 30초 단위라 21개(제한 없음 포함)였다. 너무 촘촘해서 휴대폰에서 고르기 번거롭다.

**정한 것**
- 목록: 30초, 1분, 2분, 3분, 5분, 10분, 30분, 제한 없음, 직접 설정.
- 직접 설정: 분 단위 정수로 1~60분. 더 길게 하려면 "제한 없음"을 고른다.
  - 분과 초를 따로 받는 방법도 있었다. 하지만 30초는 목록에 있고, 1분 30초 같은 시간은 거의 쓰지 않는다.
  - 범위를 넓게(예: 3시간) 두는 방법도 있었다. 하지만 오래 걸리는 방은 "제한 없음"과 방장의 "다음 단계로"로 충분하다. 범위는 상수 하나와 DB 규칙만 바꾸면 늘릴 수 있다.
- 서버 규칙은 "30초~60분(30초 단위), 또는 제한 없음(0)"이다. 화면이 만들 수 있는 값(목록과 1~60분)은 모두 이 안에 있다. 30초 단위는 원래 규칙을 그대로 둔 것이다.
- DB: V8에서 CHECK 규칙의 최대를 600초에서 3600초로 바꿨다. 기존 방의 값은 모두 새 규칙에 맞아서 옮길 데이터가 없다.

**화면 동작** (Claude가 고름)
- 직접 설정을 고를 때 고르던 시간이 분 단위면 칸에 미리 채운다(5분 → "5"). 고치기만 하면 된다.
- 규칙에 맞지 않는 값(61, 0, 1.5, 글자)을 쓰면 그 자리에 안내가 나오고 "방 만들기"를 누를 수 없다.
- 빈칸일 때는 안내 없이 "방 만들기"만 막는다. 아직 쓰지도 않았는데 틀렸다고 하지 않기 위해서다.

**결과**
- 백엔드 테스트로 확인한 것: 30분과 60분은 서버와 DB가 받고, 60분을 넘는 값은 둘 다 막는다.
- 화면 없는 크롬으로 확인한 것: 목록 9개, 미리 채우기, 잘못된 값 막기, 직접 설정한 시간(제안 15분, 투표 60분)으로 방이 만들어지는지.

## 54. "지금 접속 중" 인원 (서비스 규칙 변경)

- 날짜: 2026-11-27
- 고른 사람: 직접 ("나가면 인원이 줄었으면 좋겠다"). 참여 인원은 그대로 두고 "지금 접속 중"을 따로 보여주는 방법은 Claude가 제안하고 직접 OK 함. 세는 방법과 하트비트 간격은 Claude가 고름

**문제**: 방에 들어왔다가 나가도 "참여 인원"이 줄지 않았다. 참여 인원은 방에 들어온 적 있는 사람 수라서 규칙대로였다. 하지만 지금 몇 명이 보고 있는지 알고 싶다는 의견이 나왔다.

**고려한 선택지**

| 선택지 | 판단 |
|---|---|
| 나가면 참여 인원을 줄인다 | 서버는 "나갔다"를 알 수 없다. 탭을 닫은 것, 새로고침, 카톡으로 잠깐 넘어간 것, 화면이 꺼진 것이 모두 "연결이 끊겼다"로만 보인다. 참여 인원은 정원(50명)과 "N명 중 M명 끝냄"에 쓰여서, 잠깐 나간 사람이 빠지면 그 사람 없이 단계가 넘어갈 수 있다 |
| **참여 인원은 그대로 두고 "지금 접속 중"을 따로 보여준다 (고름)** | "참여 인원 5명 · 지금 접속 중 3명"처럼 숫자 두 개를 보여준다. 접속 중은 보여주기만 하고 규칙에는 쓰지 않아서, 잘못 세어도 진행이 망가지지 않는다 |
| 브라우저가 떠날 때 "나간다" 신호를 보낸다(`sendBeacon`) | 더 빨리 줄어든다. 하지만 새로고침에도 신호가 가서 숫자가 깜빡이고, 휴대폰에서 다른 앱으로 갈 때는 신호가 가지 않는다. 지금은 하트비트로 충분하다 |

"제한 없음" 단계에서 특히 쓸모가 있다. "5명 중 4명 끝냄 · 지금 접속 중 4명"이 보이면, 방장은 한 명이 나가서 안 넘어간다는 것을 알고 "다음 단계로"를 누를 수 있다.

**세는 방법** (Claude가 고름)
- SSE로 연결된 참여자 수를 센다. 한 사람이 탭을 여러 개 열어도 한 명이다.
- 서버 메모리의 연결 목록(`RoomChannels`)으로 센다. SSE 보내기와 같은 한계가 있다. 서버를 여러 대로 늘리면 이 목록을 서버끼리 나눠야 한다.
- 숫자가 바뀌면 모두에게 방 상태를 다시 보낸다. 숫자는 새 사람이 연결하거나, 끊긴 연결을 정리할 때 바뀐다. 같은 사람이 탭을 하나 더 열 때는 숫자가 그대로라 새 연결에만 보낸다.
- 요청에 대한 응답에서는 요청한 사람도 접속 중으로 센다. 처음 들어오는 사람은 참여 응답을 받은 뒤에 SSE로 연결한다. 그래서 이렇게 하지 않으면 자기를 뺀 인원(방을 만든 사람은 "0명")이 잠깐 보인다.
- 연결 목록을 나누는 일(보내는 쪽에서 떼어 `RoomChannels`로)은 동작을 바꾸지 않는 커밋으로 먼저 했다. 응답 항목 검사 테스트에도 `connectedCount`를 넣었다. 숫자뿐이라 누가 접속 중인지는 드러나지 않는다.

**끊긴 연결 알아채기** (Claude가 고름)
- 서버(서블릿)는 브라우저가 연결을 닫아도 바로 알려주지 않는다. 무언가를 보내 봐야 실패해서 안다.
- 그래서 하트비트를 25초에서 10초로 줄였다. 연결마다 10초에 주석 한 줄이라 보내는 양은 아주 적다.
- 실제로 재 보니, 끊긴 연결에 처음 보내는 것은 성공한 것처럼 보이고 두 번째에 실패했다. 운영체제가 보낼 내용을 일단 받아 두기 때문이다. 상대가 "이미 닫혔다"고 답한 뒤에야 다음 보내기가 실패한다. 그래서 줄어들기까지 10초보다 짧은 적이 없다.

**결과**
- 탭을 닫은 뒤 "지금 접속 중"이 줄어들기까지 걸린 시간. 연결을 닫는 순간을 0~10초 사이에서 매번 다르게 해서 6번씩 쟀다.

  | 연결 | 평균 | 가장 빠름 | 가장 느림 |
  |---|---|---|---|
  | 백엔드에 바로 | 13.9초 | 10.1초 | 19.5초 |
  | 개발 서버(Vite) 프록시를 거쳐 | 14.5초 | 10.6초 | 19.3초 |

- 새 사람이 연결하면 1ms 안에 늘어났다.
- 백엔드 테스트 6개를 새로 추가했다.
  - 접속 중이 늘고 주는지
  - 참여 인원은 그대로인지
  - 탭 여러 개는 한 명인지
  - 방마다 따로 세는지
  - 숫자가 바뀔 때만 다시 보내는지
  - 응답에서 요청한 사람을 세는지
- 이 기능 때문에 기존 SSE 테스트 하나도 고쳤다. 두 번째 사람이 연결하면 첫 사람도 "접속 중 2명"을 받으므로, 그 이벤트를 먼저 받고 넘어간다.

## 55. 뽑힌 사람의 안내 문구

- 날짜: 2026-11-27
- 고른 사람: 직접 (문장을 직접 제안함). Claude는 다른 후보와 비교해서 그대로 쓰기를 추천함

**문제**: 랜덤 선택이 "제한 없음"일 때 뽑힌 사람에게 "시간 제한이 없어요. 천천히 정해도 돼요."가 보였다. 맞는 말이지만 재미가 없다.

**고려한 후보**
1. "진짜 내가 좋아하는 걸로 가자!"
2. "재촉하는 사람 없어요. 진짜 먹고 싶은 걸로 골라요."
3. "오늘 메뉴는 내 손에 달렸다!"

**선택과 이유**: 1번.
- 카드 제목이 "내가 뽑혔어요!"라서 "내가"로 말하는 말투가 이어진다. 다른 문장은 "-요"로 끝나는데 이 줄만 반말이라, 뽑힌 사람의 속마음처럼 읽힌다.
- 아무도 고르지 않아서 뽑은 것이니, 눈치 보지 말고 정하라는 뜻과도 맞다. 3번은 오히려 부담을 준다.
- "시간 제한 없음"은 남은 시간 자리에 이미 보이므로, 이 줄에서 다시 말하지 않아도 된다.
- 모두 한 번씩 뽑혀 시간 제한이 풀린 경우에는 "모두 한 번씩 뽑혀서 이제 시간 제한이 없어요. 진짜 내가 좋아하는 걸로 가자!"다. 이때는 남은 시간 자리가 비어 있어서, 시간 제한이 없다는 말을 앞에 둔다.
